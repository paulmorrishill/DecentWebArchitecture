# 01 — Principles

The rules in this file are the ones the rest of the specification follows from. When a
later file appears to conflict with this one, this one wins, and the conflict is a
defect in the later file.

---

## 1. The dependency rule

The backend is split into four things: **domain**, **application**, **infrastructure**,
and an **entrypoint**. Dependencies point one way only.

```
entrypoint  ──►  application  ──►  domain
                    ▲
infrastructure ─────┘   (implements interfaces the application declares)
```

**Rule:** `application/` never imports from `infrastructure/` or from the entrypoint.

That is the single rule that makes the rest pay off:

- Use cases are testable with plain in-memory objects. No container, no test database,
  no mocking framework, milliseconds per test.
- Swapping a store, a mail sender, or a queue is an isolated change inside one
  `infrastructure/` folder.
- A reader can follow what wires what by reading the entrypoint top to bottom. There is
  no runtime decorator magic and no service locator.

**Enforcement:** add a lint rule or a guard test that fails the build on an import from
`application/` to `infrastructure/`. Do not rely on review. See
[12-testing-integration-and-guards](12-testing-integration-and-guards.md).

---

## 2. The API is a black box

The only thing a client knows about the server is the request and response contract for
the endpoint it calls. Nothing else crosses that line.

- A domain entity type must not appear in a contract, at the root or nested.
- The use case maps domain → contract before returning.
- The generated client is produced from the contract, not from the server's internals.

**Why:** the moment a client can name a server-internal type, changing that type becomes
a client-breaking change and the server stops being free to evolve.

---

## 3. One endpoint, one use case, one pair of contract types

Every endpoint is exactly one class with one `execute` method, one request type, and one
response type. No endpoint shares a contract type with another endpoint, even when the
two shapes are identical today.

**This looks like duplication and it is the most useful rule in the set.** Shared
contract types create an obligation that does not exist: a field added to one endpoint's
response appears on another endpoint's response, implying functionality that endpoint
does not have, and the compiler agrees with the lie.

Corollary: if a request grows a `mode: 'create' | 'update'` discriminator, that is two
use cases. Split it.

---

## 4. Generated code is generated on every build, and never committed

Code generated from the source of truth (contracts, clients, route tables,
authorization tables) is:

1. **generated by a script**, never by hand,
2. **ignored by version control**,
3. **regenerated as a mandatory step of every build, every deploy, and every local
   start**, with a contract violation failing the build.

**Generated artifacts are not committed.** A committed generated file is a merge conflict
on every branch that touches a contract, and resolving that conflict by hand is how a
generated file stops matching its source. Generating on every build removes the class
entirely: the artifact the running system uses is always derived from the source in the
same revision, so it cannot be stale and there is nothing to review a diff of.

The consequence to manage is that a fresh clone has no generated files, so generation
runs before anything that reads them — install, typecheck, lint, test, build, dev start.
Wire it into each of those commands rather than into a person's memory.

See [06-api-contract-and-codegen](06-api-contract-and-codegen.md) § 6 for what replaces
the diff check where an artifact carries security meaning.

---

## 5. Explicit composition, no container

Dependencies are constructor parameters. Wiring happens in one composition root per
entrypoint. There is no service locator, no ambient container resolution outside the
root, and no reflection-driven injection.

- A collaborator a use case cannot work without is a **required** constructor parameter.
  Optional-chaining a call to an injected collaborator (`this.thing?.do()`) converts
  "this was never wired" into "did nothing, reported nothing".
- Where composition selects between a real implementation and a no-op, it **logs which
  one it selected**, at startup. Otherwise a misconfigured environment is
  indistinguishable from a working one.

---

## 6. Time, identity, and randomness are injected

- **Never read the ambient clock inside a use case.** `DateTime.Now`, `new Date()`,
  `Date.now()`, `System.currentTimeMillis()` — a global function a test cannot replace
  without freezing global time, and a frozen global clock leaks between tests.
- **Reading time through an injected collaborator is fine, and is the normal answer when
  a use case needs more than one reading.** A `Clock` port, constructor-injected, with a
  fake in tests. Two readings across a long operation, a timeout comparison, a scheduled
  window — all legitimate.
- **A single "now" for the whole request is the common case**, and putting it on the
  request context as an ISO-8601 string is the cheapest way to get it: the entrypoint
  reads the clock once and every use case in that request agrees on the value. Use this
  where one timestamp is what the work needs; use the port where it is not.
- Identifier generation uses a standard UUID/ULID function, called in the use case, not
  in the repository and not in the database. Where a test needs deterministic identifiers,
  inject the generator instead.
- Anything else non-deterministic — randomness, the hostname, the environment — is a
  port.

**The rule is not "no time in a use case". It is that every non-deterministic value a use
case reads must come from something a test can replace.**

## 7. Expected failures are declared outcomes; unexpected ones are exceptions

Two kinds of failure, handled two different ways. Keeping them apart is the whole rule.

**An expected failure is part of the contract.** The order does not exist. The name is
taken. The caller may not do this. The state machine forbids it. These are outcomes the
use case was written to produce, so they are **declared**, and the caller branches on
them.

Two shapes, both valid — pick one per project and never mix them:

- **A closed set of typed errors** the use case throws and the entrypoint maps to
  statuses: `ValidationError → 400`, `UnauthorizedError → 401`, `ForbiddenError → 403`,
  `NotFoundError → 404`, `ConflictError → 409`.
- **A result object** carrying `successful` plus a list of error values declared on the
  response type itself. Reference implementation B's choice, and the stronger one where
  the language makes exhaustive matching cheap: the failures are in the contract, so the
  generated client sees them and the compiler can require the caller to handle each.

Either way, **each distinct failure gets its own value with its own message.** A single
lumped "something went wrong" on the server guarantees a single lumped "something went
wrong" in the interface, and a test assertion that more than one path satisfies.

**An unexpected failure is an exception, and it is allowed to propagate.** A store that
is unreachable, a null nobody anticipated, a bug. The entrypoint catches whatever reaches
it, reports it with the request id, and returns a 500 carrying that id and nothing else.
That is correct behaviour, not a gap: an unforeseen failure has no meaningful thing to
say to the caller, and inventing one hides it.

What is banned is the middle: **throwing an ad-hoc error to signal a failure the use case
knew about.** A bare error thrown for "not found" is an expected outcome dressed as a
crash — it reaches the client as a 500, it cannot be branched on, and it pollutes the
error reports with failures that are working as designed.

---

## 8. Silent recovery is banned; recovery is fine

Every catch block either rethrows or reports through the project's error reporter.

Banned in every language: an empty catch, a catch that returns a default without
logging, a rejected-promise handler that returns null.

Related and worse, because there is no error to catch at all:

- **work that never ran** — a detached asynchronous call, an unwired collaborator, a
  no-op implementation selected by configuration,
- **work that half ran** — a tool that exited zero and did less than it was asked.

Both are covered in [17-observability-and-errors](17-observability-and-errors.md) and [22-pitfalls-checklist](22-pitfalls-checklist.md).

## 9. A test is evidence only when it can fail

Before a green test counts:

- Break the thing under test and watch the test go red.
- Never assert something more than one outcome of the code satisfies.
- Never compare the code under test against a second copy of its own logic.
- A test double must enforce the constraint the real thing enforces, or the test is
  scoped to what the double omits and says so.

Full doctrine in [11-testing-unit](11-testing-unit.md).

## 10. Size and boundaries

- One file, one purpose. When a file grows past the point where its purpose can be
  stated in a sentence, it is doing two things.
- A unit is well-bounded when you can answer three questions without reading its
  internals: what does it do, how do you call it, what does it depend on.
- Prefer many small, named, independently testable units over a few large ones. This is
  a correctness argument, not an aesthetic one: an agent reasons better about code it
  can hold in context at once, and edits are more reliable in focused files.

---

## 11. Pagination is a design decision, made up front

Any endpoint returning a collection that grows with usage is paginated from the first
version. "It is only ever a handful of rows" is a statement about the seed data, not
about production.

The matching UI pages or virtualises. The matching test seeds hundreds of rows. See
[19-performance-and-scale](19-performance-and-scale.md).

---

## 12. Don't build what nothing asks for

Remove speculative features from every design before writing it down. An unused
abstraction is not free: it is a thing every future reader must understand and every
future change must preserve.

Specifically resist:

- a generic `Repository<T>` base with `save`/`findOne` — domain-named methods are easier
  to fake, easier to read, and cannot be called with the wrong intent,
- a plugin system with one plugin,
- a configuration option with one value,
- an abstraction introduced "so we can swap it later" where nothing has proposed a swap.

The dependency rule already gives the swappability. A second layer of indirection on top
of it buys nothing.

---

## 13. What "done" means

A change is done when **all** of these are true. Not most.

- [ ] It does what was asked, in full. Scope was not quietly narrowed.
- [ ] The build passes across every package.
- [ ] Unit tests pass, and the new ones have been seen to fail for the right reason.
- [ ] Integration tests pass where the change touches persistence.
- [ ] The relevant end-to-end specs pass, run more than once, with retries disabled.
- [ ] Generation ran and reported no contract violation. The generated files are absent
      from the diff, because they are not tracked.
- [ ] The infrastructure plan was reviewed if infrastructure changed, and shows no
      unintended replacement of a stateful resource.
- [ ] The pitfalls checklist was walked for the areas the change touches.
- [ ] A decision record exists if the change made a decision worth recording.

A partially-working result is reported as broken. Green ticks for the parts that worked
never appear above a failure.
