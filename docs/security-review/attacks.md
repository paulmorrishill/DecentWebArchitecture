# Attack catalogue

The attacks a tester should try against a system built to this set, and whether a rule here should stop each one. Use it as the plan for a manual pass or a penetration test ([33-security-review](../33-security-review.md) § 5). It is ordered by where in the architecture the attack lands, not by severity.

- **Repo rule.** ✅ a rule here, if followed, meets the item. 🟡 a rule meets part of it. ❌ no rule. ➖ the architecture as written has no such surface. 🏢 an organisational, people or physical control that an architecture cannot cover. **A tick is not a pass.** It says where to look; the reviewer still checks. A ✅ here means the attack *should* fail. Try it anyway — the rule is only as good as the code that follows it.
- **Test ids** are from the OWASP Web Security Testing Guide v4.2. Ids marked *(latest)* exist only in the guide's development version, which renames INPV to INJT. Blank means the guide has no test for it; the row's "what to try" is the test.
- **Tracker.** [attacks.csv](attacks.csv) has the same rows with empty result columns.
- **Set up first:** one account per role, in two tenants and two branches. Most of the attacks in the first block need two of something.
